RAG 學習日誌 Week 1

不用 LangChain, 從零寫一個 RAG, 然後老實量測它到底準不準. 2026-10-22

我是做 Linux 系統出身的工程師, 最近開始接觸 LLM 應用. 第一週的目標很單純: 先懂原理, 再用框架. 所以我只用 numpy, sentence-transformers 與 Anthropic SDK, 寫了一個約 170 行的最小 RAG, 並為它做了一組 20 題的評估集.

0.50hit@3 (8 / 16 題)
~170行程式, 無框架
20題評估集, 含邊界題

做了什麼

  • 切塊: 固定長度滑動視窗 (400 字元, 重疊 80).
  • 嵌入與檢索: 多語言 MiniLM 模型, 向量正規化後以矩陣相乘計算 cosine similarity, 取前 k 名.
  • 生成: 提示詞要求只依資料回答, 句尾標 [編號] 引用, 資料不足就拒答.
  • 量測: 每次請求記錄檢索與 LLM 的耗時, 以及 token 數 (成本的起點).
  • 評估: 自己寫 eval.py, 用 hit@k 量化檢索, 另外測拒答.

什麼是 hit@3

前 3 個檢索結果裡, 有沒有包含正確答案所在的文件. 有就算命中. RAG 的品質有個上限: 正確資料沒被撈出來, 模型再強也答不對. hit@k 就是在量這個上限, 不用呼叫 LLM, 不花 API 費用, 可以反覆重跑.

文件集是 20 位華語藝人的公開維基條目. 20 題分五種題型, 其中 4 題沒有固定的正確文件 (3 題全庫統計題, 1 題應該拒答), 所以 hit@3 只計 16 題.

我學到的事

1. 檢索分數不能當相關度

檢索錯誤的題目, 最高分也有 0.62 到 0.73, 比不少答對的題目還高. 所以「分數低於門檻就視為無關」這個直覺做法, 在這組資料上行不通.

2. 點名人物的問題反而常失敗

第 3, 4, 5, 9, 13, 15, 17 題的問題都明確寫了藝人名字, 但撈回來的卻是別人的文件. 我的假設 (尚未驗證): 切塊後的段落不一定含有人名; 小型多語言模型對專有名詞的區分力有限; 簡繁體差異也可能有影響. 下週會用實驗驗證, 而不是憑感覺相信.

3. 有些問題 top-k 檢索本來就答不好

像「哪些藝人拿過金曲獎最佳演唱」這種需要掃過全部文件的統計題, 模型只能根據撈到的 3 位藝人回答, 而且它誠實地說「資料不足」. 這不是調參數能解決的, 要靠多次查詢或事先整理成結構化資料.

4. 「答對」有時是巧合

有一題模型回答「資料中找不到答案」, 看起來很正確. 但仔細查才發現是因為正確文件根本沒被撈到, 而那份文件其實有相關資訊. 所以評估不能只看最後答案, 要把檢索與生成分開看.

5. API 回傳的 content 是一串區塊, 不是一段文字

我一開始寫死取 content[0].text, 結果模型先回了一個推理區塊 (thinking block), 程式就炸了. 這種錯誤是間歇性的: 同一份程式有時成功, 有時失敗. 正確做法是走訪所有區塊, 只取文字型別的.

text = "".join(b.text for b in msg.content if b.type == "text")
樣本只有 20 題, 一題就差 5 個百分點, 這些數字只能當方向參考, 不是結論.

下一步

每次只改一個變數, 用同一組 20 題比較 hit@3:

  1. 切塊時在每個 chunk 前加上標題 (藝人名).
  2. 加入 BM25, 並用 RRF 融合關鍵字與向量排名.
  3. 調整 chunk size 與 overlap.
  4. 統一簡繁體, 確認影響.
