第 2 週：換一份更難、更真實的資料

我把藝人維基條目換成公開的 Ubuntu linux-oem-7.0 kernel changelog：18 個版本，一個版本一個檔案，切成 3,588 個 chunk。這是我工作上會讀的文件，對檢索來說也很難：一長串 patch 標題、驅動名稱、OV02C10 這種晶片型號、0xC05 這種十六進位代碼，而且版本號只寫在每個檔案開頭一次。

我寫了 20 題新題目，分五種題型（單一事實、多行整合、跨版本、推理題例如「我在版本 X，這個修好了嗎？」，以及兩題應該拒答的），每題答案都對照 changelog 原文確認過。

  • 向量 baseline：hit@3 = 13/18 = 0.72。沒打中的 5 題全都跟精確字串或版本號有關。
  • 實驗：每個 chunk 前面加上版本標題。沒有改善（還是 0.72），一題變對、另一題變錯。embedding 模型不會把版本字串當成要精確比對的東西。
第 2 週的結論：版本號、十六進位代碼這種精確字串，本來就不是 embedding 擅長的。這直接指向關鍵字檢索。

第 3 週：BM25、hybrid，和更公平的測試

加了什麼

  • BM25，用 numpy 手寫（約 40 行）。斷詞時保留 0xc05、ov02c10、1018.18 這類字串，讓它們可以精確比對。
  • Hybrid 檢索，用 RRF 融合。向量和 BM25 各取前 50 名，再用 Reciprocal Rank Fusion（倒數排名融合）合併：每個 chunk 在每份名單得到 1/(60 + 名次) 分。它只看名次，所以兩邊差很多的分數尺度（cosine 0–1、BM25 0–50）不用先標準化。
  • 加權 RRF：BM25_WEIGHT=2 讓 BM25 的貢獻變兩倍。
  • 一個開關切換：python eval.py --oem --bm25 或 --hybrid。

第一次的結果：好得太誇張

只用 BM25 拿到 18/18，hybrid 17/18。先別高興，我回頭看題目：這些題目是我邊讀 changelog 邊寫的，用字幾乎一樣，天生對關鍵字檢索有利。真實使用者不會打「oversized UATS command」，而是說「我的 wifi 一直出問題」。

所以我加了 8 題換句話說的題目

每題都用使用者描述症狀的方式問，避開 changelog 裡的驅動名稱、晶片型號和 bug 標題。例如原文是「Fix hang on shutdown with TBT3 connected」，題目寫成「插著 Thunderbolt dock 關機時電腦會當掉」。

我學到的事

1. 評估集決定了結論

題目照抄原文時，BM25 看起來完美；換成使用者的說法後，每種方法都只對 3 題以下。如果我在第一次就停下來，會得到錯誤的結論。從此之後，用使用者的話寫題目是我建評估集的固定步驟。

2. Hybrid 不會自動比較好

換句話說的題目，向量和 BM25 各對 3 題，但對的是不同的題（向量：Q21、Q23、Q26；BM25：Q23、Q25、Q28）。兩者聯集有 5/8，hybrid 卻還是只有 3 題。RRF 獎勵的是在兩份名單都排前面的 chunk。兩邊各自找到不同答案時，兩個答案互相拉低，最後是「兩邊都還可以」的 chunk 勝出。

3. 加權也救不了

把 BM25 權重調成兩倍，結果反而稍微變差（19/26）。問題不在哪一邊比較大聲，而是兩份名單幾乎沒有重疊。

4. 真正的瓶頸是 embedding 模型

現在用的是小型、通用的多語言 MiniLM。理解換句話說本來就是向量該擅長的事，它卻只對 3/8。向量那一邊本身夠強，hybrid 才幫得上忙。

換句話說只有 8 題，差 1 題就是 12 個百分點。這些數字看方向，不是最終定論。

下一步

  1. 換一個英文檢索模型（例如 BAAI/bge-small-en-v1.5），四種方法全部重跑。程式不用改，模型是環境變數。
  2. 如果向量變強，再試 hybrid；如果沒有，改試在 BM25 + 向量的候選上加 cross-encoder reranker。
  3. 從問題裡解析版本號當過濾條件（針對「版本 X 修好了沒」這類題目）。
