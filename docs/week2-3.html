RAG Learning Journal: Weeks 2–3

Keyword search, hybrid search, and an eval set that tells the truth. 2026-11-07

In week 1 I built a minimal RAG without a framework. This update covers what came next: I moved it to a new dataset (a public Linux kernel changelog), added keyword search (BM25) and hybrid search, and then rewrote part of the eval set because the first result looked too good to be true.

Week 2: a harder corpus

I replaced the artist Wikipedia pages with the public Ubuntu linux-oem-7.0 kernel changelog: 18 versions, one file per version, 3,588 chunks. It is hard for retrieval: long lists of patch titles, driver names, chip IDs like OV02C10, hex codes like 0xC05, and the version number written only once at the top of each file.

I wrote 20 new questions in five types (single fact, multi-line, cross-version, reasoning such as "is this fixed if I am on version X?", and two that should be refused), and checked every answer against the changelog.

  • Vector baseline: hit@3 = 13/18 = 0.72. The five misses were all about exact strings or versions.
  • Experiment: prefix every chunk with its version title. No change (still 0.72). One question became a hit, another became a miss. The embedding model does not treat a version string as something to match exactly.
Conclusion of week 2: exact strings such as version numbers and hex codes are not something embeddings are good at. That pointed straight at keyword search.

Week 3: BM25, hybrid search, and a fairer test

What I added

  • BM25, written by hand in numpy (about 40 lines). The tokenizer keeps strings like 0xc05, ov02c10 and 1018.18 as single tokens, so they can match exactly.
  • Hybrid search with RRF. Vector and BM25 each return their top 50, and Reciprocal Rank Fusion merges them: every chunk scores 1/(60 + rank) from each list. It uses only ranks, so the two very different score scales (cosine 0–1, BM25 0–50) don't need to be normalized.
  • Weighted RRF: BM25_WEIGHT=2 doubles BM25's contribution.
  • One switch for all of it: python eval.py --oem --bm25 or --hybrid.

First result: too good

BM25 alone scored 18/18 and hybrid 17/18. Before celebrating, I looked at the questions: I had written them while reading the changelog, so they reuse its exact words. That favours keyword search by construction. Real users don't type "oversized UATS command"; they say "my wifi keeps failing".

So I added 8 reworded questions

Each one describes a symptom the way a user would and avoids the changelog's driver names, chip IDs and bug titles. For example, "the computer freezes when I power off with a Thunderbolt dock plugged in" for the entry "Fix hang on shutdown with TBT3 connected".

What I learned

1. The eval set decides the conclusion

With questions copied from the source text, BM25 looked perfect. With reworded questions, every method got 3 of 8 or fewer. If I had stopped at the first run, I would have drawn the wrong conclusion. Writing questions in the user's words is now part of how I build eval sets.

2. Hybrid is not automatically better

On the reworded questions, vector and BM25 each got 3 right, but different ones (vector: Q21, Q23, Q26; BM25: Q23, Q25, Q28). Together they cover 5 of 8, yet hybrid still got only 3. RRF rewards chunks that rank well in both lists. When each method finds a different answer, the two answers push each other down and something "fairly good in both" wins.

3. Weighting did not fix it

Giving BM25 twice the weight made the result slightly worse (19/26). The problem is not which side is louder; the two lists barely overlap.

4. The real bottleneck is the embedding model

The model is a small, general-purpose multilingual MiniLM. Understanding a reworded question is exactly what vectors are supposed to be good at, and it only got 3 of 8. Hybrid can only help once the vector side is strong on its own.

With 8 reworded questions, one question is 12 percentage points. These numbers show direction, not a final verdict.

Next steps

  1. Swap in an English retrieval model (for example BAAI/bge-small-en-v1.5) and re-run all four methods. No code change: the model is an environment variable.
  2. If the vector side improves, retry hybrid; otherwise try a cross-encoder reranker on the BM25 + vector candidates.
  3. Use the version number in the question as a filter (for "is this fixed in version X" questions).
