1. 從零開始：模型是什麼

模型就是一份寫死的計算食譜加上一大堆數字。輸入的文字先轉成數字，照食譜做幾億次乘法和加法，輸出另一串數字。

  • 權重（weights）：食譜裡那堆數字，是訓練時學出來的。這次的 embedding 模型約 1.2 億個（檔案 471 MB），Qwen2.5-1.5B 約 15 億個。
  • 推論（inference）：拿訓練好的模型算新的輸入。這次只做推論，不訓練。
  • token：模型處理文字的最小單位，大約是英文字的一部分或一個中文字。
推論的本質是「大量、重複、可以同時做的乘加法」。哪種晶片擅長同時做很多簡單運算，就會算得快又省電。這是整個實驗的出發點。

2. RAG 裡的兩種模型

RAG（檢索增強生成）= 先從資料裡找出相關段落，再請語言模型根據這些段落回答。它用到兩種模型：

Embedding 模型LLM（大型語言模型）
這次用的paraphrase-multilingual-MiniLM-L12-v2Qwen2.5-1.5B-Instruct（int4）
輸入 → 輸出一段文字 → 384 個數字（向量）問題 + 參考段落 → 一個字一個字產生的回答
比喻圖書館員，把每本書的「意思」編成一個座標寫作者，讀完資料後寫出答案
在 RAG 裡的工作建索引，以及每次查詢時轉換問題最後產生答案

向量怎麼找資料：意思接近的文字，向量也接近。「NPU 驅動修正」和「accel/ivpu: fix ...」的向量會靠得很近。所以找資料 = 把問題轉成向量，再找距離最近的 chunk。

  1. 切塊：18 個版本的 kernel changelog 切成 3588 個 chunk（每塊約 400 字元）。
  2. 建索引：embedding 模型把每個 chunk 轉成向量，存成 index.npz。要算 3588 次，最吃重。
  3. 查詢：問題也轉成向量（算 1 次），找出最接近的 4 個 chunk。
  4. 生成：問題 + 4 個 chunk 組成 prompt，交給 LLM 寫答案。

第 2、3 步是 embedding benchmark 量的；第 4 步是 LLM benchmark 量的。

LLM 不建索引，那它怎麼回答？

LLM 不建索引，也不負責找資料。三者分工：

  1. embedding 模型：建索引；問問題時找出最相關的 4 個 chunk。
  2. 程式（rag.py 的 build_prompt）：把這 4 段文字直接貼進 prompt，變成「根據以下資料回答：[1]…[4]… 問題：…」。
  3. LLM：只讀這份 prompt，照著內容寫出答案。
LLM 像考試時拿到參考資料的學生：資料由檢索挑好交給它，它負責讀完寫答案。檢索沒挑對資料，LLM 再強也答不對，這就是 hit@3 要量的事。也因為 4 段資料都塞進 prompt，LLM 每次要先讀約 780 個 token，這就是第 8 節「第一個字」要等的原因。

3. Hugging Face、PyTorch、Optimum、OpenVINO

角色是什麼比喻
Hugging Face放開源模型的網站，也出 transformers、sentence-transformers、optimum 等 Python 套件食譜圖書館
PyTorchMeta 的 AI 框架，真正執行模型運算；Hugging Face 上多數模型是它的格式通用廚房
Optimum（optimum-intel）Hugging Face 的轉換工具，把 PyTorch 格式轉成 OpenVINO 格式；optimum-cli 是它的指令翻譯官
OpenVINOIntel 的推論工具，為 Intel CPU / GPU / NPU 最佳化。PyTorch 不支援 NPU，所以要用它Intel 專用廚房

OpenVINO 的三個步驟

  1. 轉換（只做一次）：Hugging Face 的 PyTorch 模型 NPU 看不懂。optimum-intel 把它轉成 OpenVINO 的 IR 格式（.xml 描述食譜、.bin 放數字），存在 ov_models/。embedding 模型由 embed_ov.py 自動轉；LLM 用 optimum-cli 手動轉。
  2. 編譯（每種晶片一次）：OpenVINO 把 IR 編譯成某種晶片的程式。NPU 這步特別久，結果快取在 ov_cache/，下次直接用：所以 NPU 的 compile_s 只要 0.19 秒。
  3. 執行：編譯好的程式透過驅動送進晶片。NPU 的路徑是 OpenVINO → Level Zero → intel_vpu kernel 驅動 → /dev/accel/accel0。

ov_models/ 和 ov_cache/ 都在 .gitignore 裡，刪掉也只是下次重新產生。

4. CPU、GPU、NPU 差在哪

Core Ultra 7 155H 是一顆 SoC，三種運算單元在同一顆晶片裡，共用記憶體和電源。

CPUGPU（內顯）NPU（Intel AI Boost）
比喻幾位萬能的資深工程師一大群工讀生，同時做簡單的事專門做矩陣乘法的機器
擅長什麼都能做、邏輯複雜的工作大量平行運算（畫面、AI）只做 AI 推論，但很省電
限制同時做的事少，算 AI 耗電功耗中等不能跑一般程式；只吃固定大小的輸入

固定大小（靜態形狀）是 NPU 的重要限制：所以 embedding 一律把每段文字補或切成 128 個 token、一次送 8 段（查詢時送 1 段）。為了公平，CPU 和 GPU 也用同樣的形狀。LLM 則要事先告訴 NPU prompt 最長多少（MAX_PROMPT_LEN=2048）。

5. 環境準備

詳細步驟在 client-linux-notes 的 NPU 筆記，重點：

  • kernel 6.8 以上就有 intel_vpu 驅動（這次是 7.0），會產生 /dev/accel/accel0。
  • 從 intel/linux-npu-driver 裝 user-space 套件：intel-driver-compiler-npu、intel-fw-npu、intel-level-zero-npu、libze1。
  • 帳號加入 render 群組才能打開 accel0（sudo usermod -aG render $USER，重新登入）。
  • GPU 需要 intel-opencl-icd。
  • ./tools/npu/check_npu.sh 一次檢查全部；最後應看到 OpenVINO 列出 CPU、GPU、NPU 三個裝置。

6. 實際操作：每個指令在做什麼

pip install -r requirements.txt -r bench/requirements-bench.txt

# 資料：Ubuntu linux-oem-7.0 kernel changelog，每個版本一個檔
python scripts/fetch_oem_changelog.py                 # -> data/oem-7.0/

# 準確度（eval 會用索引）
DATA_DIR=data/oem-7.0 python rag.py index            # PyTorch 建索引
python eval.py --oem                                   # 20 題 kernel 題庫的 hit@3
DATA_DIR=data/oem-7.0 EMBED_BACKEND=openvino EMBED_DEVICE=NPU python rag.py index
EMBED_BACKEND=openvino EMBED_DEVICE=NPU python eval.py --oem

# 速度與功耗（bench 不用索引，自己跑四種裝置）
DATA_DIR=data/oem-7.0 sudo -E .venv/bin/python bench/bench_embed.py

# 小型 LLM
optimum-cli export openvino -m Qwen/Qwen2.5-1.5B-Instruct \
  --weight-format int4 --sym --group-size -1 --ratio 1.0 ov_models/qwen2.5-1.5b-int4
DATA_DIR=data/oem-7.0 python bench/bench_llm.py --model ov_models/qwen2.5-1.5b-int4 --devices NPU --repeat 1
DATA_DIR=data/oem-7.0 sudo -E .venv/bin/python bench/bench_llm.py --model ov_models/qwen2.5-1.5b-int4

eval 和 bench 的差別

  • eval 量準不準：用索引搜尋 20 個問題，看正確版本有沒有在前 3 名（hit@3）。索引是哪個裝置建的，量到的就是那個裝置的準確度，所以 NPU 要重建索引再跑一次。
  • bench 量快不快、耗不耗電：不讀索引，直接拿 chunks.json 的文字，自己把四種裝置都跑一輪。

bench_embed.py 對每個裝置做的事

  1. 量閒置功耗 5 秒（晶片本來就會花的電，約 2.6 W）。
  2. 載入與編譯，計時 = compile_s。
  3. 建索引測試：256 個 chunk、一次 8 個，重複至少 10 秒 → 每秒幾個（index_cps）與功耗。
  4. 比對答案：和 PyTorch 算的向量比 cosine（1.0 = 完全一樣）。
  5. 查詢延遲：一次 1 個問題，重複 200 次 → p50 / p95。
  6. 休息 5 秒換下一個裝置，讓溫度回落。

為什麼有時要 sudo、有時不用

跑 NPU 不需要 root（帳號在 render 群組就夠）。只有讀功耗要 root：RAPL 是 Intel 晶片內建的電表，/sys/class/powercap/intel-rapl:*/energy_uj 預設只有 root 能讀。程式在測試前後各讀一次累積焦耳數，相減除以時間就是平均瓦數。NPU 另有 npu_busy_time_us 計數器，用來證明工作真的在 NPU 上。

試跑（只是確認能動、先把 NPU 編譯快取建好）不需要功耗，所以不加 sudo；正式量測才加。

怎麼讀

  • 快（每秒幾個）和省電（幾瓦）是兩件事：GPU 每秒做的工是 NPU 的 2.6 倍，但功率也是 2.7 倍。
  • 「每個 chunk 花多少焦耳」最公平：把快和省電合在一起看，等於「同一份工作，電池掉多少」。NPU 比 GPU 少約 22%，比 CPU 少約 13 倍。
  • NPU 單筆查詢最快（7.6 ms），一問一答時使用者感受到的是這個。
  • 工作真的在 NPU 上：NPU 使用率 94%，同時 CPU core 功率只有 0.7 W。
  • 準確度沒變：向量 cosine ≥ 0.999996；PyTorch 索引和 NPU 索引的 hit@3 都是 13/18 = 0.72，每題命中結果相同。

8. 結果二：小型 LLM

Qwen2.5-1.5B int4，3 個 kernel 問題，每題的 RAG prompt 平均 781 個輸入 token，固定生成 128 個 token，每題跑 2 次。閒置 package 功率 3.3 W。

裝置第一個字（TTFT）之後每秒 token每題總時間Package 功率每題能量（扣閒置）
CPU2.61 s41.65.7 s30.5 W155 J
GPU0.50 s33.74.3 s21.8 W79 J
NPU1.85 s21.67.7 s12.2 W69 J

LLM 的兩個階段

  • Prefill（讀 prompt）：781 個 token 可以一次平行算完，是「算力」比賽 → GPU 最快（比 NPU 快 3.7 倍）。量的是 TTFT（第一個字出來要多久）。
  • Decode（逐字生成）：每生成一個 token 都要把整個模型從記憶體讀一次，是「記憶體頻寬」比賽 → CPU 反而最快。量的是 tokens/s。

整體回答 GPU 最快；NPU 最慢，但功率只有 GPU 的 56%，每題能量還少約 13%。CPU 每題能量約是另外兩者的兩倍。

回答品質不是這次的重點：1.5B 模型在 CVE 題目上前後矛盾，還輸出簡體中文。這份量測只比速度與功耗。

10. 踩過的坑

1. 檢查腳本誤報驅動沒載入

lsmod | grep -q intel_vpu 在 set -o pipefail 下會誤判：grep -q 找到就提早結束，lsmod 收到 SIGPIPE，整條 pipeline 被當成失敗。改成檢查 /sys/module/intel_vpu 是否存在。

2. KeyError: 'token_type_ids'

這個多語言模型用 XLM-R 的 tokenizer，不產生 token_type_ids，但轉出來的 OpenVINO 模型仍要這個輸入。單句輸入時它本來就全是 0，補 0 即可。雲端測試用的小 BERT 模型剛好有產生，所以沒抓到：測試要用真的模型。

3. sudo 留下 root 的檔案

用 sudo 跑過一次後，bench/results/、ov_models/、ov_cache/ 變成 root 所有，下次不加 sudo 就 PermissionError。現在程式結束時會用 SUDO_UID 自動把擁有者改回來。

4. CPU 提早結束，數字不公平

第一次跑 LLM 時 CPU 平均只生成 45 個 token 就停了（不同裝置數值有微小差異，模型在不同地方決定結束）。讀 prompt 的能量是固定的，回答越短，平均到每個 token 越多，CPU 的 J/token 被灌水成 2.77。改成 ignore_eos，固定生成 128 個之後是 1.36。比較效能時，工作量要完全一樣。

5. OpenVINO CPU「比較慢」：其實只有查詢慢，原因是補齊

第一輪看起來 OpenVINO CPU 建索引 40.7 vs PyTorch 48.8、查詢 24.7 ms vs 12.2 ms。用 bench/bench_ov_cpu.py 一次只改一個變因，查出三件事：

變體改了什麼建索引 chunks/s（3 次中位數，最低-最高）查詢 p50執行緒
PyTorch基準35.5（34-49）22.4 ms16
ov-static固定 [8,128] / [1,128]（原本做法）58.6（41-60）27.0 ms6
ov-static-q32查詢改成固定 [1,32]42.6（42-43）7.8 ms6
ov-dynamic不固定形狀，只補到該批最長41.9（42-42）6.5 ms6
ov-static-t16要求 16 個執行緒37.2（36-37）37.0 ms14
ov-dynamic-t16動態 + 16 執行緒35.8（35-37）8.4 ms14
  • 查詢慢 = 補齊。查詢平均只有 21 個 token（p95 28），固定形狀卻補到 128，多算約 6 倍。改成固定 32 或動態形狀，查詢降到 7 ms 左右，比 PyTorch 還快。固定 32 的好處是 NPU 也能用（NPU 只吃固定形狀），而且 p95 只有 8.2 ms，最穩。
  • 建索引沒有真的比較慢。chunk 平均 124 個 token，本來就接近 128，補齊幾乎沒有浪費。同一個設定重跑，數字可以差到 1.5 倍（PyTorch 這次 35.5、上次 49；ov-static 這次 58.6、上次 43）。筆電會因為溫度和功耗上限降頻，工作被排到哪種核心也會影響，所以第一輪的差距在誤差範圍內。教訓：筆電上量效能一定要重複幾次，看最低和最高差多少。
  • 多開執行緒反而更慢。Core Ultra 7 155H 有 6 顆 P-core（大核）、8 顆 E-core（小核）、2 顆 LP E-core（省電核）。要求 16 個執行緒時實際拿到 14 個（P + E），建索引從約 42 掉到 37，查詢從 27 ms 變 37 ms。神經網路每一層都要等所有執行緒算完才能往下，E-core 比較慢，大家都在等它。OpenVINO 預設只用 6 顆 P-core 是對的。
  • 原本懷疑的 SCHEDULING_CORE_TYPE=ANY_CORE 本來就是預設值，那組實驗等於沒改東西。先印出實際生效的設定再做實驗（OVEmbedder.properties()）。

6. eval 漏掉的題目與裝置無關；在 chunk 前加版本號也沒救

5 題 MISS 在 CPU 和 NPU 上完全一樣，是檢索方法的問題：版本號只寫在檔案開頭，長版本中間切出來的 chunk 不知道自己屬於哪一版。

試了 CHUNK_TITLE=1：每個 chunk 前面加上 [linux-oem-7.0 (7.0.0-1012.12) ...] 這種標題再重建索引。hit@3 還是 13/18 = 0.72，只是換了幾題（#16 變命中，#10 變沒命中，#14 從 3/3 掉到 2/3）。原因：

  • 每個 chunk 都多了幾乎一樣的前綴，chunk 之間變得更像，反而比較難分開。
  • 模型最多讀 128 個 token，前綴佔掉位置，chunk 尾巴被截掉。
  • embedding 比的是「意思」，對「1012 和 1013」這種精確的數字或字串本來就不敏感。

比較好的方向是：關鍵字搜尋（BM25）和向量搜尋並用，或先從問題抓出版本號，只在那一版的 chunk 裡找。

12. 下一步

  1. 每個 chunk 前面加上版本號：試過，hit@3 不變（見第 10 節第 6 點）。改試 BM25 + 向量混合搜尋，或依版本號過濾。
  2. 查 OpenVINO CPU 變慢的原因：查詢是補齊造成，建索引是誤差（見第 10 節第 5 點）。
  3. NPU 查詢改用固定長度 32（bench_embed.py --query-seq-len 32），預期會比 7.6 ms 更快。
  4. embedding 試更大的 batch，看 NPU 和 GPU 的差距會不會改變。
  5. 量冷啟動：--no-cache 看 NPU 第一次編譯要多久。
