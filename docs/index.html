RAG Learning Journal: Week 1

No LangChain. I built a RAG from scratch, then honestly measured how accurate it is. 2026-10-22

I'm an engineer with a Linux systems background, and I recently started working on LLM applications. My goal for week one was simple: understand the principles first, then use frameworks. So I used only numpy, sentence-transformers and the Anthropic SDK to write a minimal RAG of about 170 lines, and built a 20-question evaluation set for it.

What I built

  • Chunking: fixed-length sliding window (400 characters, 80 overlap).
  • Embedding & retrieval: a multilingual MiniLM model; vectors are normalized, so a matrix multiply gives cosine similarity, and I take the top k.
  • Generation: the prompt requires answers only from the provided context, a [n] citation after each sentence, and a refusal when the context is insufficient.
  • Measurement: every request logs retrieval time, LLM time and token counts (the starting point for cost tracking).
  • Evaluation: my own eval.py, using hit@k for retrieval plus a refusal check.

What is hit@3?

Whether the correct source document appears in the top 3 retrieved results. If it does, that's a hit. RAG quality has a ceiling: if the right material isn't retrieved, even a strong model can't answer correctly. hit@k measures that ceiling. It needs no LLM call, costs nothing, and can be re-run as often as you like.

Results

The corpus is the public Wikipedia entries of 20 Mandarin-language artists. The 20 questions fall into five types; 4 of them have no single correct document (3 corpus-wide aggregation questions and 1 that should be refused), so hit@3 counts only 16.

What I learned

1. Similarity scores don't tell you relevance

Wrong retrievals still had top scores of 0.62 to 0.73, higher than many correct ones. The intuitive approach of treating anything below a score threshold as irrelevant doesn't work on this data.

2. Questions that name a person failed more often

Questions 3, 4, 5, 9, 13, 15 and 17 all name the artist explicitly, yet retrieval returned other people's documents. My hypotheses (not yet verified): chunks don't always contain the person's name; a small multilingual model separates proper nouns poorly; and Traditional/Simplified Chinese differences may play a role. I'll test these next week instead of trusting a hunch.

3. Some questions are a poor fit for top-k retrieval

For questions like "which artists have won a Golden Melody Award for best vocal performance", which require scanning every document, the model can only answer from the 3 artists it retrieved, and it honestly said the data was insufficient. Tuning parameters won't fix this; it needs repeated queries or pre-structured data.

4. A "correct" answer can be a coincidence

On one question the model answered "not found in the data", which looked right. On inspection, it was because the correct document was never retrieved, and that document did contain relevant information. So don't judge only the final answer: look at retrieval and generation separately.

5. The API returns a list of content blocks, not a string

I first hard-coded content[0].text, and the model sometimes returned a reasoning (thinking) block first, which crashed the program. The failure was intermittent: the same code sometimes worked and sometimes didn't. The fix is to iterate over all blocks and keep only the text ones.

text = "".join(b.text for b in msg.content if b.type == "text")
With only 20 questions, one question moves the score by 5 percentage points. Treat these numbers as direction, not conclusions.

Next steps

One change at a time, comparing hit@3 on the same 20 questions:

  1. Prefix every chunk with its title (the artist's name).
  2. Add BM25 and fuse keyword and vector rankings with RRF.
  3. Tune chunk size and overlap.
  4. Normalize Traditional/Simplified Chinese and check the effect.
