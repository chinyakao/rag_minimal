## artists/: 中文藝人維基條目 (第 1 週, 2026-10-21 至 10-23)

專案的第一個資料集. 目的是先用自己熟悉的中文內容, 跑通「切塊, embedding, 檢索, 生成」整條流程,
並建立第一份 20 題評估集. Week 1 學習日誌 ([英文](https://chinyakao.github.io/rag_minimal/),
[中文](https://chinyakao.github.io/rag_minimal/zh.html)) 寫的就是這個資料集的結果.

| 檔案 | 用途 |
|---|---|
| `fetch_wiki_artists.py` | 從中文維基百科下載 20 位華語藝人的條目, 轉成 Markdown 存到 `data/` (需設定 `WIKI_CONTACT`, Wikimedia 要求 User-Agent 帶聯絡方式) |
| `wiki_manifest.tsv` | 評估時所用條目的原始網址與版本永久連結 (維基條目會持續被編輯, 數字可能與重新下載的版本不同) |
| `eval_artists.py` | 20 題中文題庫, 原本是 `eval.py` 裡的 `EVAL_SET` |

授權: 維基條目文字是 CC BY-SA 4.0, 本 repo 不轉載內容, 只保存下載腳本.

當時的用法 (在 `5d0e052` 上):

```bash
WIKI_CONTACT=你的信箱 python scripts/fetch_wiki_artists.py
python rag.py index
python eval.py            # hit@3
python eval.py --llm      # 另外檢查拒答題
```

### 第一週練習

- [v] 換上自己的文件, 跑 `index` 與 `ask`, 觀察分數與命中的 chunk.
- [v] 在 `eval.py` 補到 20 題, 記下 baseline 的 hit@3.
- [v] 改 `CHUNK_SIZE` 與 `CHUNK_OVERLAP`, 重建索引再評估, 記錄差異.
- [v] 問一個文件裡沒有答案的問題, 看模型是否拒答.
- [v] 寫 5 行筆記: 問題, 方案, 權衡, 結果.

### Baseline 評估結果 (2026-10-22)

設定: 藝人維基文件 20 份 (`data/`), 固定長度切塊 (400 字元, 重疊 80), 向量檢索 only
(paraphrase-multilingual-MiniLM-L12-v2, cosine), 評估 k=3, 生成用 `TOP_K=4`. 題目共 20 題, 見 `eval_artists.py`.
執行指令: `python eval.py` (只看檢索) 與 `python eval.py --llm` (另測拒答與人工檢查題).

**總結: hit@3 = 8/16 = 0.50** (有固定正確文件的 16 題; 12, 14, 18, 20 題沒有固定正確文件, 不計入)

| multi_para (多段落整合) | 4/5 |
| cross (跨條目) | 1/3 |

#### 觀察

- **分數不能當相關度的依據**: 檢索錯誤的題目 top1 也有 0.62 到 0.73 (第 3, 4, 5, 9 題),
  甚至高於不少答對的題目. 所以光靠分數門檻過濾沒有用.
- **有明確人名的題目反而常失敗**: 第 3, 4, 5, 9, 13, 15, 17 題的問題都點名了藝人, 但檢索回來的是別人.
  可能原因 (尚未驗證): 切塊後的段落內容本身不一定含藝人姓名; 小型多語言模型對專有名詞的區分力有限;
  也可能受簡繁體差異影響 (例如檔名 `刘若英.md`, 題目寫 `劉若英`).
  這正是第 2 週要實驗 BM25 + RRF 混合檢索, 以及切塊時加上標題 (藝人名) 前綴的動機.
- **全庫統計題 (12, 14, 18) 本質上不適合 top-k 檢索**: LLM 的回答只涵蓋檢索到的 3 位藝人,
  並如實說明資料不足. 第 14 題只列出周杰倫與張惠妹, 沒有其他人. 這類題需要掃描全部文件 (例如 Agent 多次查詢,
  或事先建立結構化欄位), 不是調參數能解決的.
- **第 19 題的拒答是巧合, 不是正確推理**: 回答 "資料中找不到答案" 是因為蕭敬騰的文件根本沒被檢索到.
  文件裡其實有 2008 年簽華納唱片, 2014 年經紀公司喜鵲娛樂的資訊. 所以這題的問題出在檢索, 不在生成.
- **第 20 題拒答成功**, 但前 3 名都不是相關文件, 本來就沒有可引用的資料, 難度偏低.
- 兩次執行的檢索結果完全相同 (向量檢索是確定性的), 差別只在是否呼叫 LLM.

#### 當時規劃的下一步實驗 (每次只改一個變數, 用同一組 20 題比較 hit@3)

1. 切塊時在每個 chunk 前加上檔名或標題 (藝人名).
2. 加入 BM25 並用 RRF 融合 (第 2 週). 後來在 kernel changelog 資料集上實作.
3. 試不同 `CHUNK_SIZE` 與 `CHUNK_OVERLAP`.
4. 把簡體檔名 `刘若英.md` 與內容統一成繁體, 確認簡繁差異的影響.


## k8s/: Kubernetes 官方文件 (第 2 週, 2026-10-24 至 11-05)

第一個英文資料集. 目的是補上英文語料, 並用一份對我來說較陌生的技術文件, 建立第二份 20 題評估集.
後來改用 kernel changelog, 這份就沒有再延伸.

| 檔案 | 用途 |
|---|---|
| `fetch_k8s_docs.py` | 下載 28 頁 Kubernetes concepts 文件到 `data/k8s/`, 固定在某個 commit, 結果可重現 |
| `k8s_manifest.tsv` | 28 頁文件的來源網址與 commit |
| `eval_k8s.py` | 20 題英文題庫 (`EVAL_SET_K8S`), 題型與中文題庫相同 |
| `eval_k8s_answers.md` | 每題的出處與原文引文, 另附給 Linux 背景讀者的 k8s 名詞入門 |

授權: Kubernetes 文件是 CC BY 4.0, 本 repo 不轉載內容, 只保存下載腳本.

當時的用法 (在 `5d0e052` 上):

```bash
python scripts/fetch_k8s_docs.py
DATA_DIR=data/k8s python rag.py index
python eval.py --k8s
```

結果: 只用 BM25 時 hit@3 = 19/19 (2026-11-06, 雲端測試). 向量檢索的數字沒有留下正式紀錄.

## 為什麼兩個都封存

- kernel changelog 有版本號, 晶片型號, 十六進位代碼, 更能測出向量檢索與關鍵字檢索的差別.
- 一次只維護一份題庫, 每個改動都在同一組題目上比較, 結論比較清楚.
